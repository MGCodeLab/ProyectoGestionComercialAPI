## Parte 2: Iteración 1 — Estandarizar Configuraciones de Auditoría

**Problema:** Cada entidad (Producto, Cliente, TipoDocumento) repetía las mismas 10+ líneas de configuración EF para PublicId, Activo, FechaRegistro, etc.

**Solución aplicada:**
Se creó la clase abstracta `AuditableEntityConfiguration<T>` en `Infrastructure/Persistence/Configurations/`. Todas las configuraciones ahora heredan de esta clase y solo definen lo que es específico de su entidad.

**Resultado:** Código DRY, menos lugar donde cometer errores, y consistencia garantizada en todas las tablas.

**Archivos creados:**
- `Infrastructure/Persistence/Configurations/AuditableEntityConfiguration.cs`

**Archivos modificados:**
- `ProductoConfiguration.cs` — ahora hereda la base
- `ClienteConfiguration.cs` — ahora hereda la base
- `TipoDocumentoConfiguration.cs` — ahora hereda la base
- `Producto.cs` y `TipoDocumento.cs` — ahora heredan `AuditableEntity`

## Parte 3: Iteración 2 — Corrección del Soft Delete

**Lo que salió mal primero:**
Se implementó un global query filter en AppDbContext que filtraba automáticamente los registros con `Activo = false`. Parecía conveniente, pero era incorrecto para este proyecto.

**Por qué estaba mal:**
Tú indicaste que el soft delete en Nexus-ERP NO es para ocultar datos. Es una marca de auditoría. Los registros inactivos deben seguir siendo visibles en la API porque:
- El frontend los va a mostrar igual (con distinto estilo visual)
- Sirven para trazabilidad histórica
- El usuario maneja visualmente cuáles están activos y cuáles no

**Corrección aplicada:**
Se revirtió completamente el global filter. AppDbContext quedó limpio. La lógica de inactivar/activar queda en los endpoints `PATCH /{id}/inactivar` y `PATCH /{id}/activar`.

**Regla establecida:** `GET /api/v1/clientes` devuelve TODOS los registros, siempre. El frontend decide cómo mostrarlos.

## Parte 5: Setup de Base de Datos

**Problema encontrado:**
Al intentar probar la API, los endpoints fallaban con `Invalid column name 'PublicId'`. Las tablas existentes (Productos y TipoDocumentos) no tenían las columnas de auditoría que el código esperaba.

**Solución:**
Se creó el script `v3.0.0_COMPLETE_SETUP.sql` que:
1. Agrega las columnas faltantes a las tablas existentes (ALTER TABLE con IF NOT EXISTS)
2. Hace seed de datos de prueba para Productos, TipoDocumentos y Clientes

**Lección aprendida sobre SQL Server:**
`NEWSEQUENTIALID()` solo puede usarse en la definición DEFAULT de una columna (DDL), no en un INSERT VALUES. Para hacer seeds, hay que omitir la columna `PublicId` y dejar que el DEFAULT la genere automáticamente.

**Reorganización posterior:**
- El script completo se movió a `History Changed/20260425_T1800_DatabaseSetupV3/`
- Las instrucciones de uso se colocaron en `IA_Docs/DATABASE_SETUP_INSTRUCTIONS.md`
- Scripts individuales redundantes fueron eliminados

## Parte 7: Módulo de Autenticación JWT (Iteración Principal)

Esta fue la implementación más importante de la sesión. El frontend Angular tenía todo listo con un mock, y necesitaba los endpoints reales del backend.

### Contrato implementado (según spec del frontend)

**POST /api/v1/auth/login**
- Recibe: `{ email, password }`
- Devuelve: JWT token + perfil del usuario + lista completa de permisos
- Normaliza email a minúsculas antes de buscar
- Password verificado con BCrypt

**POST /api/v1/auth/logout**
- Sin lógica de backend (dummy OK)
- El frontend limpia su estado local

**GET /api/v1/auth/me**
- Requiere Bearer token válido
- Hace query a BD para datos frescos (no decodifica JWT)
- Devuelve perfil + roles + permisos actualizados

### Estructura del dominio creada

Se crearon 5 entidades en `Domain/Seguridad/`:
- `Usuario` — con Nombre, Email, PasswordHash, LastLogin
- `Rol` — con Nombre, Descripcion
- `Permiso` — con Recurso (ej: "productos") y Accion (ej: "create")
- `UsuarioRol` — tabla pivot (sin AuditableEntity, es solo relación)
- `RolPermiso` — tabla pivot (sin AuditableEntity, es solo relación)

### JWT configurado

- Algoritmo: HS256
- Claims en el token: sub, email, nombre, roles, iat, jti
- Expiración: 60 minutos (configurable)
- Clave en appsettings.json bajo sección `Jwt`

### Decisión arquitectónica importante (BCrypt)

El LoginHandler en Application layer no puede usar BCrypt directamente porque Application no debe tener dependencias de paquetes externos de infraestructura.

**Solución:** La verificación de password (`BCrypt.Verify`) vive en `UsuarioService` (Infrastructure). El método `AutenticarUsuario(email, password)` retorna el `Usuario` con sus roles y permisos si las credenciales son válidas, o `null` si no. El Handler solo verifica si es null.

### Usuarios de prueba creados (seed en BD)

| Email | Password | Rol | Acceso |
|-------|----------|-----|--------|
| admin@nexus.com | 123456 | ADMIN | Todos los permisos del sistema |
| vendedor@nexus.com | 123456 | VENDOR | create/edit/view en productos, clientes, ventas |
| readonly@nexus.com | 123456 | READ_ONLY | Sin permisos asignados |

### Permisos del sistema definidos

Los recursos son: `productos`, `clientes`, `ventas`, `usuarios`  
Las acciones son: `create`, `edit`, `delete`, `export`, `activate`, `deactivate`, `audit_access`, `view`

### Pipeline de autenticación en ASP.NET

Se agregó en `Program.cs`:
```csharp
app.UseAuthentication();  // ← nuevo, antes de UseAuthorization
app.UseAuthorization();
```

Y la configuración de JWT Bearer con validación de Issuer, Audience y firma.

### Nuevas excepciones

Se creó `UnauthorizedException` que el middleware global captura y convierte en HTTP 401. Se agregó `UnauthorizedResponse()` en `ControllerExtensions`.

### Consideraciones para Ventas
- Una venta tiene cabecera (cliente, fecha, total) y múltiples líneas (producto, cantidad, precio)
- Crear una venta debe ser atómico (cabecera + todas las líneas en una sola transacción)
- Si una línea falla, toda la venta debe hacer rollback
- Esto justifica implementar UnitOfWork explícito para ese módulo

## Notas Importantes

### Sobre la Jwt Key en appsettings.json
Actualmente la clave JWT está en `appsettings.json` en texto plano. Esto está bien para desarrollo, pero para producción debe migrarse a:
- Variables de entorno
- Azure Key Vault
- Secrets Manager

### Sobre [Authorize] en controllers existentes
ProductosController y ClientesController actualmente no tienen `[Authorize]`. Están "abiertos". Esto es intencional por ahora para no romper el flujo de desarrollo mientras el frontend conecta la autenticación real. Una vez confirmado que el Bearer token llega, se activa.

### Sobre los warnings de nullable
Los 3 warnings de nullable en los DTOs de Producto son preexistentes y no afectan el funcionamiento. Se pueden resolver agregando `= string.Empty` en las propiedades string, pero no son prioritarios.
