## 🔧 Trabajo Realizado

### 1. Resolución de SQL Constraint Violation (CRÍTICO)

**Problema encontrado:**
```
SqlException: Violation of UNIQUE KEY constraint 'UQ_Clientes_Correo'
The duplicate key value is (<NULL>)
```

**Root cause identificada:**
SQL Server trata múltiples valores NULL como duplicados cuando hay UNIQUE constraint, aunque el campo es nullable. Esto bloqueaba la creación de clientes sin email.

**Solución implementada:**
Reemplazar la constraint UNIQUE tradicional con un **índice filtered** que solo enforza unicidad cuando el valor NO ES NULL.

**Cambios específicos:**

1. **Archivo: `Database/02_Tablas/03_Clientes.sql`**
   - Removido: `CONSTRAINT UQ_Clientes_Correo UNIQUE (Correo)`
   - Agregado: Índice filtered después de CREATE TABLE
   ```sql
   CREATE UNIQUE INDEX UQ_Clientes_Correo
       ON comercial.Clientes(Correo)
       WHERE Correo IS NOT NULL;
   ```

2. **Archivo: `Database/03_Seeds/FIX_UpdateCorreoConstraint.sql` (NUEVO)**
   - Script de migración para bases de datos existentes
   - Verifica y elimina constraint antigua
   - Crea índice filtered
   - Idempotente (puede ejecutarse múltiples veces)

**Beneficios de esta solución:**
- ✅ Múltiples clientes sin email (NULL) — permitido
- ✅ Clientes con email unique — enforced
- ✅ Flexible para negocio: "El email es opcional pero si existe debe ser único"
- ✅ Seguir patrón SQL Server best practice para campos nullable + unique

**Testing recomendado después de aplicar:**
```sql
-- Esto debe permitirse ahora
INSERT INTO comercial.Clientes (TipoDocumentoId, NumeroDocumento, Nombres, ApellidoPaterno, Correo)
VALUES (1, '12345678', 'Juan', 'Pérez', NULL),
       (1, '12345679', 'Maria', 'García', NULL);  -- Dos NULLs en Correo, sin error

-- Esto debe fallar (email duplicado)
INSERT INTO comercial.Clientes (TipoDocumentoId, NumeroDocumento, Nombres, ApellidoPaterno, Correo)
VALUES (1, '12345680', 'Pedro', 'López', 'juan@example.com'),
       (1, '12345681', 'Pablo', 'López', 'juan@example.com');  -- Error: UNIQUE violation
```

## 📊 Decisiones Tomadas en Esta Sesión

### Decisión 1: Índice Filtered para Email Nullable
**Tipo:** Arquitectura de BD  
**Impacto:** Alto (afecta validación de datos)  
**Decisión:** Usar `CREATE UNIQUE INDEX ... WHERE IS NOT NULL` en lugar de UNIQUE constraint

**Razones:**
- Permite múltiples NULLs sin error
- Más flexible para negocio: email opcional pero único si existe
- Patrón recomendado por Microsoft SQL Server

**Alternativas consideradas:**
- ❌ Hacer email NOT NULL → Rechazado (clientes sin email son válidos)
- ❌ Remover constraint completamente → Rechazado (permite duplicados)
- ✅ Índice filtered → ACEPTADO (mejor balance)

**Referencia:** `IA_Docs/DATABASE_ARCHITECTURE.md` sección "Unique Indexes with NULL Handling"

## 🎓 Aprendizajes & Mejores Prácticas Establecidas

1. **SQL Server + Nullable Unique Fields:** Usar filtered indexes, no constraints
2. **Computed Columns:** Declarar en Configuration.cs AND SQL DDL (not one or the other)
3. **AutoMapper:** Siempre bidireccional, nunca asignación manual
4. **DTOs:** Validación + XMLdoc + required keyword
5. **Documentación:** Estratificada por audiencia (devs, IAs, ejecutivos)
6. **Soft Delete:** Es auditoría, no ocultación (GET retorna todos)
7. **Passwords:** BCrypt HS256, cost factor 11-12, exactamente 60 chars
8. **Schema Versionado:** Sin EF Migrations, scripts manuales en Database/
