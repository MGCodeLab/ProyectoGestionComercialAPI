## 🎯 Decisiones Arquitectónicas Principales

### 1. Soft Delete as Audit Trail (NOT Data Hiding)

**Decisión:** `Activo = 0` marca registro como eliminado, pero NO se filtra en queries.

**Justificación:**
- Auditoría: Historial completo de operaciones
- Cumplimiento: Requisitos legales de auditoría
- Recuperación: Reactivar registros si es necesario
- Transparencia: Reportes muestran qué se eliminó y cuándo

**Implementación:**
```csharp
// ❌ NUNCA hacer esto
.HasQueryFilter(x => x.Activo == true);  // Esto rompe el principio

// ✅ CORRECTO
var clientes = await _dbContext.Clientes.ToListAsync();  // Retorna TODOS
```

**Endpoints:**
- `GET /api/v1/clientes` → 100 activos + 5 inactivos = 105 registros
- `PATCH /inactivar` → Soft delete (reversible)
- `DELETE /` → Hard delete (irreversible, solo si no tiene dependencias)

### 2. Filtered Unique Indexes for Nullable Unique Fields

**Decisión:** Usar índices filtered en lugar de constraints tradicionales para campos NULL + UNIQUE.

**Problema original:**
```sql
CONSTRAINT UQ_Clientes_Correo UNIQUE (Correo)
-- SQL Server trata múltiples NULLs como violación de constraint
-- Causa: Violates UNIQUE KEY constraint aunque Correo IS NULL
```

**Solución implementada:**
```sql
CREATE UNIQUE INDEX UQ_Clientes_Correo
    ON comercial.Clientes(Correo)
    WHERE Correo IS NOT NULL;
```

**Beneficios:**
- ✅ Permite múltiples NULLs sin error
- ✅ Enforza unicidad para valores no NULL
- ✅ Flexible para negocio: "Email opcional pero único si existe"
- ✅ Patrón recomendado por Microsoft SQL Server

**Cuándo aplicar:**
- Campos nullable que deben ser únicos si no NULL
- Ejemplos: Email (opcional), Username secundario, código alterno

---

### 3. Computed Columns (PERSISTED)

**Decisión:** Usar computed columns SQL para datos calculados que se consultan frecuentemente.

**Caso de uso: NombreCompleto (Cliente)**

**Declaración Triple (OBLIGATORIA):**

1. **Entity (Domain):**
```csharp
public class Cliente : AuditableEntity
{
    public string Nombres { get; set; }
    public string ApellidoPaterno { get; set; }
    public string ApellidoMaterno { get; set; }
    
    // Computed property
    public string NombreCompleto { get; set; }
}
```

2. **Configuration (Infrastructure):**
```csharp
public class ClienteConfiguration : AuditableEntityConfiguration<Cliente>
{
    public override void Configure(EntityTypeBuilder<Cliente> builder)
    {
        base.Configure(builder);
        
        builder.Property(x => x.NombreCompleto)
            .HasComputedColumnSql(
                "[Nombres] + ' ' + [ApellidoPaterno] + ' ' + ISNULL([ApellidoMaterno], '')",
                stored: true);  // PERSISTED = almacenado en disco
    }
}
```

3. **DDL (Database):**
```sql
CREATE TABLE comercial.Clientes
(
    ...
    NombreCompleto AS [Nombres] + ' ' + [ApellidoPaterno] + ' ' + ISNULL([ApellidoMaterno], '') PERSISTED,
    ...
);
```

**Razones:**
- `PERSISTED` = almacenado en disco (no recalculado cada vez)
- Indexable para búsquedas rápidas
- NULL handling automático
- Datos siempre sincronizados

**Regla:** Si falta en cualquiera de los 3 lugares → Error de runtime

### 4. AutoMapper Bidirectional Mappings

**Decisión:** Usar `.ReverseMap()` para mappings bidireccionales consistentes.

**Patrón obligatorio:**
```csharp
// En Profile.cs
CreateMap<Cliente, ClienteDto>().ReverseMap();
CreateMap<CrearClienteDto, Cliente>();
CreateMap<ActualizarClienteCommand, Cliente>().ReverseMap();
```

**En Handlers:**
```csharp
// ✅ CORRECTO
_mapper.Map(command, cliente);  // Una línea, automático

// ❌ NUNCA
cliente.Nombres = command.Nombres;
cliente.ApellidoPaterno = command.ApellidoPaterno;
// ... 15 líneas más
```

**Beneficios:**
- Mantenibilidad: Un cambio en DTO = actualizar mapper una vez
- Consistencia: Todos los handlers usan mismo patrón
- Reducción de bugs: No hay asignaciones manuales olvidadas

---

### 5. CQRS Pragmático (No Completo)

**Decisión:** MediatR solo para Commands (creación/modificación), Services para Queries (lectura).

**Justificación:**
- Commands = lógica de negocio compleja → MediatR + validación
- Queries = lectura directa → Services simples, sin overhead

**Estructura:**
```
Commands (MediatR):
├── CrearClienteCommand + Handler + Validator
├── ActualizarClienteCommand + Handler + Validator
├── EliminarClienteCommand + Handler
└── ActualizarEstadoClienteCommand + Handler

Queries (Services):
├── IClienteService.ObtenerTodos()
├── IClienteService.ObtenerPorId(id)
└── No hay validación ni handlers separados
```

**Ventajas:**
- Balance entre estructura y pragmatismo
- CQRS donde aporta valor real
- Evita sobreingeniería innecesaria

## 🐛 Problemas Encontrados & Solucionados

### Critical Issue #1: UNIQUE Constraint Violation on NULL Values

**Severidad:** 🔴 CRÍTICA (bloqueaba creación de clientes sin email)  
**Encontrado:** Sesión actual (2026-04-30)  
**Status:** ✅ RESUELTO

**Síntoma:**
```
Microsoft.Data.SqlClient.SqlException:
Violation of UNIQUE KEY constraint 'UQ_Clientes_Correo'.
Cannot insert duplicate key in object 'comercial.Clientes'.
The duplicate key value is (<NULL>).
```

**Root Cause:**
SQL Server trata múltiples valores NULL como duplicados para UNIQUE constraints, aunque SQL estándar indica NULL ≠ NULL.

```sql
-- PROBLEMA
CONSTRAINT UQ_Clientes_Correo UNIQUE (Correo)
-- Insert dos registros con Correo = NULL
-- Primera inserción: OK
-- Segunda inserción: VIOLATION (aunque ambos son NULL)
```

**Diagnóstico:**
- Se intentaba crear cliente sin email (Correo = NULL)
- SQL Server rechazaba por constraint
- El email es opcional en negocio, pero si existe debe ser único

**Solución:**
Reemplazar constraint tradicional con **índice filtered** que solo aplica donde IS NOT NULL:

```sql
-- SOLUCIÓN
DROP CONSTRAINT UQ_Clientes_Correo;

CREATE UNIQUE INDEX UQ_Clientes_Correo
    ON comercial.Clientes(Correo)
    WHERE Correo IS NOT NULL;
```

**Archivos modificados:**
1. `Database/02_Tablas/03_Clientes.sql` — DDL actualizado
2. `Database/03_Seeds/FIX_UpdateCorreoConstraint.sql` — Migration script
3. `Infrastructure/Persistence/Configurations/ClienteConfiguration.cs` — Configuration updated

**Testing realizado:**
- ✅ Insert con Correo = NULL (permitido, sin error)
- ✅ Insert con Correo duplicado (rechazado, como se espera)
- ✅ Insert con Correo = NULL dos veces (ambos permitidos)

**Regla extraída:**
Para cualquier campo nullable que deba ser único → usar filtered index, no constraint

### Critical Issue #3: BCrypt Password Hash Verification Failure

**Severidad:** 🔴 CRÍTICA (autenticación rota)  
**Encontrado:** Sesión anterior (2026-04-28)  
**Status:** ✅ RESUELTO

**Síntoma:**
```csharp
BCrypt.Net.BCrypt.Verify("123456", hash) → always false
```

**Root Cause:**
Hashes generados manualmente con trailing dot (61 chars en lugar de 60):
```
❌ $2a$12$92IXUNpkjO0rOQ5byMi.Ye4oKoEa3Ro9llC/.og/at2uheWG/igi.
✅ $2a$12$92IXUNpkjO0rOQ5byMi.Ye4oKoEa3Ro9llC/.og/at2uheWG/igi
```

**Solución:**
1. Generar hashes correctos con cost factor 11-12:
```csharp
var hash = BCrypt.Net.BCrypt.HashPassword("123456", workFactor: 12);
```

2. Verificar longitud: exactamente 60 caracteres

3. Insertar en seed sin trailing characters

**Regla extraída:**
- BCrypt HS256, cost factor 11-12
- Hash length: exactamente 60 caracteres
- Verificar siempre con `.Verify()` antes de insertar

## 📏 Reglas Nuevas / Actualizadas

### Regla #1: Filtered Unique Indexes para NULL + UNIQUE

**Categoría:** Database Design  
**Aplicable:** Campos nullable que deben ser únicos  
**Obligatorio:** SÍ

```sql
-- Patrón obligatorio para campos nullable + unique
CREATE UNIQUE INDEX IX_TableName_FieldName
    ON schema.TableName(FieldName)
    WHERE FieldName IS NOT NULL;
```

**Excepciones:** Ninguna. No usar CONSTRAINT UNIQUE en campos nullable.

---

### Regla #2: Triple Declaration para Computed Columns

**Categoría:** Entity Framework + Database Design  
**Aplicable:** Todas las computed columns  
**Obligatorio:** SÍ

```csharp
// 1. Entity (Domain)
public string NombreCompleto { get; set; }

// 2. Configuration (Infrastructure)
.HasComputedColumnSql("[formula]", stored: true)

// 3. DDL (Database)
NombreCompleto AS [formula] PERSISTED
```

**Regla:** Si falta uno de los tres → Error de runtime

---

### Regla #3: Siempre ReverseMap() en AutoMapper

**Categoría:** Application Pattern  
**Aplicable:** Todos los mappings bidireccionales  
**Obligatorio:** SÍ

```csharp
// ✅ CORRECTO
CreateMap<Cliente, ClienteDto>().ReverseMap();
CreateMap<ActualizarClienteCommand, Cliente>().ReverseMap();

// ❌ INCORRECTO
CreateMap<Cliente, ClienteDto>();  // Sin ReverseMap
```

---

### Regla #4: Nunca Asignación Manual en Handlers

**Categoría:** Code Pattern  
**Aplicable:** Todos los handlers (MediatR)  
**Obligatorio:** SÍ

```csharp
// ✅ CORRECTO
_mapper.Map(command, entity);

// ❌ INCORRECTO
entity.Field1 = command.Field1;
entity.Field2 = command.Field2;
// ... líneas manuales
```

---

### Regla #5: Soft Delete es Auditoría, no Ocultación

**Categoría:** Business Logic  
**Aplicable:** Todas las queries GET  
**Obligatorio:** SÍ

```csharp
// ✅ CORRECTO - Retorna todos (activos + inactivos)
var items = await _dbContext.Items.ToListAsync();

// ❌ INCORRECTO - Oculta registros
.HasQueryFilter(x => x.Activo == true)
```
